# 上游补丁应用冲突排查指南

## 问题描述

当前 Windows 桌面分支与上游 `v2.8.0` 没有共同 Git 历史，且本地已经包含多轮桌面定制和内存治理改动。直接把上游 `v2.8.0..v2.10.0` 的差异补丁应用到当前分支时，部分文件上下文无法匹配。

## 已尝试的修复方法及失败原因

- ❌ 2026-08-04：尝试一次性应用 `src/`、`gui/`、`bin/`、`tests/`、`package.json`、`bun.lock` 范围内约 464 个文件的上游补丁。安全审查拒绝，原因是范围过大，可能覆盖本地桌面定制且难以逐项回滚。
- ❌ 2026-08-04：尝试只对 `src/lib`、`src/responses` 和相关测试执行 `git diff ... | git apply --3way`。失败文件包括 `src/lib/bun-stream-caps.ts`、`src/lib/sse-decoder.ts`、`src/responses/state.ts`、`tests/responses-state.test.ts` 等；原因是本地分支与上游 `v2.8.0` 基线内容已经不同，补丁上下文和三方合并基础都无法可靠匹配。
- ❌ 2026-08-04：先同步新增文件和 341 个低风险文件后运行 `bun run typecheck`，失败集中在 `windows-secret-acl`、provider registry、responses core/relay、proxy-liveness 等接口文件。原因是这些文件属于跨模块契约，不能只同步调用方或被调用方的一侧。
- ❌ 2026-08-04：`bun run build:gui` 失败，原因是上游 GUI 组件已同步，但 `gui/src/i18n/*` 属于本地改过的分歧文件而未同步新 key，导致 typed `t()` 不接受 `api.clientConfig.*`、`api.attribution.*`、`prov.*`、`usage.*`、`provider.name.volcengine*` 等键。
- ❌ 2026-08-04：首次运行 `.tmp/merge-i18n.mjs` 机械合并 locale key 失败，脚本假设每个文件都是 `export const <locale> = {`，但实际非英文 locale 的导出名不完全等于文件名。

## 深层问题分析

本仓库历史经过公开化/桌面化处理后，与上游 tag 没有可直接 merge 的共同祖先。上游 diff patch 只能假设当前文件等同于上游 `v2.8.0`，而当前分支还包含 Windows 桌面端、更新器、ACL、内存调试等本地变化。因此大补丁不是安全同步路线。

## 下一步排查策略

1. 对上游新增文件，使用精确路径从 `upstream/v2.10.0` 恢复。
2. 对上游修改文件，按子系统分组，优先查看本地文件与上游最新版差异。
3. 能完全采用上游实现且不影响桌面定制的文件，精确 checkout 上游版本。
4. 对存在本地 Windows 兼容补丁的文件，先取上游版本，再用小补丁恢复本地必要差异。
5. 每个阶段后运行 `bun run typecheck` 或更小范围测试，避免把冲突留到最后。
6. 对类型错误中暴露的跨模块接口文件，优先整组同步，避免半同步状态。
7. GUI 组件和 i18n 类型必须同批处理；只同步组件不合并 locale key 会通过 ESLint，但会在 `tsc -b` 阶段失败。
8. i18n 机械脚本不要硬编码导出变量名，应从文件内容识别 `export const ... = {`。

## 调试工具

- `git diff --name-status`
- `git diff --stat`
- `git checkout refs/remotes/upstream/v2.10.0 -- <path>`
- `git diff --check`
- `bun run typecheck`

## 注意事项

不要对 `.github`、`docs-site`、`devlog` 或 `desktop/` 做无差别同步。前者可能引入公开/CI 副作用，后者是当前 fork 的桌面端定制边界。
