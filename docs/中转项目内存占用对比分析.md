# 中转项目内存占用对比分析

## 结论

`cockpit-tools`、`cc-switch` 和 OpenCodex 都可以承担本地中转/路由角色，所以当前 OpenCodex/Bun 进程 1GB+ 内存占用不能简单归因于“它是中转站”。结合本机诊断，主要异常信号是 OpenCodex 运行时 `activeTurnCount` 达到 224-227，而当前实际 Codex active 任务只有两个；最近请求日志也大多已有 `terminal/completed`。这更像 WebSocket turn 生命周期释放链漏掉了某些关闭/替换路径。

进一步对比本地 Git 历史后，结论需要收紧：当前 Windows fork 相对本地 `origin/main`（v2.8.0，上游仓库 metadata 仍指向 `lidge-jun/opencodex`）只在 `src/server/index.ts` 做了 9 行 `startServer` hostname option 变更；`lifecycle.ts`、`ws-bridge.ts`、`responses/core.ts` 都没有 fork 侧差异。因此当前观察到的 active turn 释放风险不是 Windows 桌面端改造新增的核心逻辑，而是 fork 继承的 v2.8.0 runtime 行为。

同时，上游 `lidge-jun/opencodex` 当前 `main` 已经出现 `tryAdmitTurn` / `ActiveTurnLease` / `turnAdmissionLease` 一类生命周期硬化代码。本 fork 当前工作树没有这些符号，说明它落后于上游后续修复方向。Windows 桌面端会放大可见性：任务管理器把 Bun sidecar 归到 `opencodex · proxy dashboard` 进程树，Bun/JSC 在 Windows 下的 `external` / `jscHeap` 指标也更容易表现为高驻留；但真正需要对齐的是 runtime 释放语义。

## OpenCodex 当前风险点

- `src/server/lifecycle.ts` 用全局 `Set<AbortController>` 统计 active turns，`registerTurn` / `unregisterTurn` 必须严格成对。
- `src/server/index.ts` 的 WebSocket `response.create` 分支创建 `turnAbort`，注册后在 async turn 的 `finally` 中释放。
- `src/server/ws-bridge.ts` 的 `pumpResponsesSseToWebSocket` 内部会把 `ws.data.cancel` 覆盖为 reader cancel。这样 close/supersede 时调用到的取消函数，可能只 cancel SSE reader，没有触发上层 `turnAbort.abort()`。
- 如果 reader cancel 或 upstream stream 在 Bun/Windows 下挂住，async turn 的 `finally` 不执行，`activeTurns` 就会长期增长，并连带保留 request/log context、Response body reader、闭包对象等内存。

## cockpit-tools 对照

源码位置：`reference/cockpit-tools`

- 桌面壳是 Tauri/Rust，Codex API 代理核心是 Go sidecar `cockpit-cliproxy`。
- `ResponsesWebsocket` 在连接级别创建 `passthroughSessionID`，并用 `defer` 统一释放 tool cache、关闭 upstream execution session、关闭 downstream WebSocket。
- `forwardResponsesWebsocket` 在每条流式结果路径里显式调用 `cancel(...)`：客户端断开、错误、写失败、流提前结束、正常完成都会收尾。
- `internal/wsrelay/session.go` 有 60 秒读超时、10 秒写超时、30 秒 heartbeat；pending request 在终止消息、ctx cancel 或 session cleanup 时会 `LoadAndDelete` 并关闭 channel。

参考点：

- 把“连接级资源”和“单 turn 资源”分层：连接关闭时清 session，单 turn 完成时清请求缓存。
- 取消函数不要被覆盖丢失；下层 reader cancel 和上层 request abort 必须组合调用。
- 给 WebSocket upstream/relay 加 read/write deadline、heartbeat 和 pending 清理。

## cc-switch 对照

源码位置：`reference/cc-switch`

- proxy 直接写在 Tauri/Rust 后端，`ProxyServer` 用 shutdown channel 和 server `JoinHandle` 管理生命周期，停止时有 5 秒等待保护。
- `session.rs` 明确是“轻量化实现，仅提取 session_id 用于日志记录，不做复杂的 Session 管理”。
- `ActiveConnectionGuard` 用 RAII 方式维护 `active_connections`，流式 body future 被 drop 时自然回收计数。
- `create_logged_passthrough_stream` 只保存当前 SSE buffer、UTF-8 残片和必要 usage 事件；支持首包超时和静默超时。
- `SseUsageCollector.finish()` 使用 `std::mem::take` 清空事件数组，并有 `SseUsageFinishGuard` 在异常 drop 时兜底触发 finish。

参考点：

- active 计数应由资源生命周期驱动，而不是依赖分散出口路径手动维护。
- 流式统计缓存要在 finish/drop 时清空，不能无限保留事件数组。
- session id 只做日志关联，避免把会话级状态扩大成常驻内存结构。

## 建议优化方案

1. 先修 WebSocket cancel 链。`pumpResponsesSseToWebSocket` 接收外部 cancel/abort hook，或保存旧的 `ws.data.cancel` 并组合调用，保证 close/supersede 同时 abort upstream turn 和 cancel SSE reader。
2. 增加 active turn 诊断。`/api/system/memory` 可增加 active WebSocket 数、active WS response turn 数、最长 turn 年龄、按状态聚合数量；只暴露标量，不暴露请求体、账号、token、路径。
3. 增加 watchdog。对 WebSocket response turn 添加最大静默时间和最长生命周期，超时后主动 abort、释放 active turn，并记录 499/502。
4. 给 release 链路补回归测试。模拟永不结束的 SSE body、客户端 close、下一条 `response.create` supersede，断言 `activeTurnCount` 回到基线。
5. 收紧日志/usage 热路径。已知 `responseState.totalBytes` 只有约 63MB，不是这次大头；但仍应确保流式事件缓存 finish 后清空，日志只保留必要摘要。
6. 中期再考虑 native sidecar。Go/Rust sidecar 确实能降低 JS/JSC 常驻压力，但在 `activeTurnCount` 泄漏修复前迁移 runtime 性价比不高，容易把生命周期 bug 搬到另一层。

## 判断边界

- 本地 `origin/main` 是 v2.8.0 基线，`package.json` repository 指向 `https://github.com/lidge-jun/opencodex.git`。
- `origin/main..HEAD` 在内存相关路径中只有 `src/server/index.ts` 的 `startServer(port, { hostname })` 改动，和 WebSocket turn 注册/释放无关。
- WebSocket `response.create` 的 `registerTurn(turnAbort)`、`finally unregisterTurn(turnAbort)`、`pumpResponsesSseToWebSocket` 覆盖 `ws.data.cancel` 这些代码，在本地 `origin/main` 和当前 HEAD 中一致。
- 上游当前 `main` 已经有新的 turn admission/lease 代码，本 fork 尚未对齐；后续修复应优先评估 cherry-pick/backport 这类上游修复，而不是只做 Windows 专用 workaround。
- 目前证据最强的是“实际 active 任务数量远小于 `activeTurnCount`”，不是“多 agent 本身吃掉 1GB”。多 agent 会制造很多请求，但正常完成后不应留下 200+ active turns。
