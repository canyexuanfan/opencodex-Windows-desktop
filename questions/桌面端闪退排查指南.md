# 桌面端闪退排查指南

## 问题描述

用户反馈本机安装的 OpenCodex Windows 桌面端刚刚出现闪退，且此前也偶发过类似情况。本轮先做只读取证，不重启当前 Codex 会话，不停止真实 OpenCodex/Codex 进程。

## 已尝试的修复方法及失败原因

- ❌ 2026-08-03：尝试用 `Get-CimInstance Win32_Process` 读取 OpenCodex/Bun/Codex 父子进程和命令行，当前权限返回 `HRESULT 0x80041003 / 拒绝访问`。该路线不能继续重复，需改用低权限证据链。
- ❌ 2026-08-03：默认沙箱读取 `C:\Users\wzm33\.opencodex\runtime-port.json` 返回 `UnauthorizedAccessException / 访问被拒绝`。该文件在用户目录且由真实 OpenCodex 写入，失败更像当前命令沙箱边界；下一步用最小范围授权只读 runtime 文件和本地 healthz，不读取 token。
- ❌ 2026-08-03：默认沙箱列 `C:\Users\wzm33\AppData\Local\CrashDumps` 返回 `UnauthorizedAccessException / 访问被拒绝`。不能把无法列 dump 误判为无 dump；下一步用最小授权只列文件名、时间和大小，不读取 dump 内容。
- ✅ 2026-08-03：授权只读 `runtime-port.json` 并请求本地 `/healthz`，确认当前代理健康：`pid=36640`、`port=10100`、`service=opencodex`、版本 `2.8.0`。用户随后澄清这是手动重新打开后的状态，因此该证据只能说明重开后正常，不能证明闪退时 backend 自动恢复或一直在线。
- ✅ 2026-08-03：查询 10:50-11:15 的 Windows Application/System 错误日志，没有 `OpenCodex.exe` 相关 `Application Error` / `Windows Error Reporting`，也没有同时间段系统错误。
- ✅ 2026-08-03：授权只列 `CrashDumps` 文件名/时间/大小，今天没有新的 OpenCodex dump；最近相关 dump 是 2026-08-01 06:59 的 `codex.exe.42444.dmp`，路径属于官方 Codex App，不是 `E:\Program\OpenCodex\OpenCodex.exe`。
- ✅ 2026-08-03：`Get-Process OpenCodex` 显示多个 OpenCodex 进程仍在响应，但 `MainWindowHandle=0`、`MainWindowTitle` 为空，说明当前没有可见主窗口；结合 `desktop/src/main.ts` 中 `mainWindow.on("close")` 会 `preventDefault()` 并 `hide()`，本轮现象更像窗口被隐藏到托盘或 renderer/window 层消失，而不是主进程硬崩溃。

## 深层问题分析

桌面端由 Electron 主进程托管 dashboard，并由 `DesktopBackendSupervisor` 拉起内置 Bun sidecar。当前代码对 sidecar 的 `stderr` 直接丢弃，Electron 主进程也没有稳定落盘日志；因此真实安装包闪退时，需优先结合 Windows 事件日志、WER/CrashDumps、`.opencodex/crash.log`、`runtime-port.json`、进程启动时间和安装目录来判断。

已知代码中注册了 `render-process-gone` 并尝试重载 dashboard；若用户看到的是窗口消失但后台 sidecar 仍存活，可能是 Electron renderer/GPU/window 层问题。若 WER 存在 `OpenCodex.exe` APPCRASH，则应优先按 native 崩溃处理。

本轮没有找到 `OpenCodex.exe` 的 WER/CrashDump 硬崩溃证据；`.opencodex/crash.log` 11:05:59 的最新条目为 `benign-abort-teardown (Bun fetch-body abort; proxy unaffected)`，不应作为桌面端闪退根因。用户澄清 11:11 的健康进程是手动重新打开产生的，因此当前不能断言闪退时 backend 仍存活；只能判断本轮没有 OS 级硬崩溃记录。代码目前缺少 Electron 主进程和 sidecar stderr 的落盘日志，导致无法精确还原窗口层为何消失或主进程为何退出。

## 下一步排查策略

1. 查询最近几小时 Windows Application 事件日志里是否存在 `OpenCodex.exe`、`bun.exe`、`electron` 相关 `Application Error` 或 `Windows Error Reporting`。
2. 检查 `C:\Users\wzm33\.opencodex\crash.log` 尾部，区分 `benign-abort-teardown` 噪声和真正 fatal/uncaught/panic。
3. 检查 `C:\Users\wzm33\AppData\Local\CrashDumps`、WER `ReportArchive/ReportQueue` 是否有 11 点左右的 OpenCodex dump。
4. 只读确认当前 `runtime-port.json` 与 OpenCodex/Bun 进程是否已重新拉起，避免误把恢复后的状态当作崩溃现场。
5. 如果没有可用主进程日志，后续修复方向优先增加 Electron 主进程/sidecar stderr 的本地日志留存，再复现。

## 调试工具

- `Get-WinEvent -FilterHashtable @{LogName='Application'; StartTime=...}`
- `Get-Process OpenCodex,bun,codex -ErrorAction SilentlyContinue`
- `.opencodex/crash.log`
- `.opencodex/runtime-port.json`
- `AppData\Local\CrashDumps`
- `C:\ProgramData\Microsoft\Windows\WER\ReportArchive`

## 注意事项

- 不要为了取证重启或关闭当前 Codex/OpenCodex 会话。
- 不要读取或转述 `admin-api-token`、请求体、账号标识等敏感内容。
- 没有 WER/CrashDump 时，不能把 sidecar 的 benign abort 噪声误判成桌面端硬崩溃。
